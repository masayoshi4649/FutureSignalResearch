# 研究の進め方と保存方針

作成日：2026-10-30。

## 1. 役割と前提

本リポジトリでは、NK225先物・TOPIX先物のラージの価格・板を観測して、チャート分析と自動発注の仮説を検証する。将来の構成は、サーバーからWebSocketを受信し、足と指標を更新し、売買を判断し、注文と建玉を管理するもの。mini・microへの移用は商品別の執行条件を区別する。

保有期間はデイ08:45〜15:45、ナイト17:00〜翌06:00のそれぞれ1セッション内。取引所のザラバと板寄せを区別し、終了後は建玉と未約定注文を残さない設計を研究する。現在は教科書と検証方針を整備した段階で、自動注文システムや実測の損益は未作成である。

| 場所 | 保存するもの |
| --- | --- |
| `docs/` | 教科書、複数試行で再利用する知見、データ仕様、出典、目次 |
| `study/` | 5桁番号付きの試行ごとの仮説・結果・再現条件・Viewer互換資料 |
| `work/` | AIが自由に使用する一時作業、展開、キャッシュ、生成途中のファイル。Git管理外 |
| `../JP_OSE_Data/` | 共用の過去データ。各試行に複製せず参照する |
| `../SessionTradeViewer/` | 価格・建玉・損益を確認する既存アプリ。形式は実装と仕様を参照する |

`work/` はどれだけ汚してもよい作業領域とする。研究を再現するために必要な唯一のコード・入力条件・結果を、ここにしか置かない状態では試行完了としない。一時物を整理する時期は任意でよい。

## 2. 試行番号

試行フォルダは `study/00001_要約/` の形式とする。番号は既存最大値の次を使用し、同じ番号を再利用しない。要約は何を比較する試行か分かる短い日本語とする。例：`study/00001_MACD交差と方向条件の比較/`。

一つのフォルダに、先に定めた候補比較やパラメータ探索をまとめてよい。その場合、採用候補だけでなく全候補の数・設定・結果を小さな表で残す。結果を見た後に仮説や主な入口・出口を変更する場合は、新しい番号へ送る。元の記録は残し、変更の理由を相互リンクする。

教科書作成は実データの試行に数えない。現時点では最初の番号を消費していない。

## 3. 試行の最小構成

```text
study/
  00001_要約/
    README.md                 仮説、条件、結果、限界、次の問い
    条件.json                 パラメータ、入力参照、版、費用、期間分割
    集計.csv                  セッション別・候補別の小さな集計
    一覧.resources.json       Viewerの資源一覧
    約定.trades.jsonl          原則として約定片だけ
    判断.jsonl                必要な場合だけ、理由・判断時刻・原板行
    再現用コード等             共有実装への参照で足りなければ保存
```

ファイル名のうち、Viewerの形式を識別する `.resources.json` と約定内容は[データと閲覧形式](データと閲覧形式.md)に従う。`条件.json`・`集計.csv`・`判断.jsonl` は本研究用であり、Viewerが直接読み込む仕様とはみなさない。共通の正式スキーマや検証エンジンは、最初の実試行で必要に応じて決める。

原板、既存CSV、全ティック指標、毎ティック会計、大量の画像やHTMLレポートは標準成果物として重複保存しない。約定がなくてもREADMEと集計を残す。約定ファイルは空にできるが、評価したセッション自体を消さない。

注文要求・取消・拒否と、実際の約定は別の事実である。Viewer用の約定JSONLに未約定の要求を混ぜず、運用を研究する段階では必要な注文イベントを別に保存する。要約から原因を追跡できない取引は、理由と必要最小限の指標を記録する。

## 4. 再現に必要な情報

| 分類 | 記録事項 |
| --- | --- |
| 入力 | データルートからの相対パス、セッション、銘柄、限月、サイズ、内容のハッシュ、観測範囲 |
| 版 | 研究コード、データ、Viewerのコミット。未追跡・変更済み入力は内容でも識別 |
| 足と指標 | 価格系列、区間、確定時点、初期化、前セッションの利用、欠損処理、式とライブラリ版 |
| 手法 | 全条件、候補数、比較対象、数量、新規・返済・保護・期限の優先順位 |
| 執行 | 実行商品、倍率、呼値、気配方向、遅延・待ち行列・部分約定・同時計の仮定 |
| 費用 | 手数料の採用日と根拠、価格に含めた滑り、別費用との二重控除防止 |
| 評価 | 開発と未使用の期間、主指標、品質基準、除外、持ち越しの監査、判定不能 |
| 実行 | 実行日時、コマンド、依存関係、乱数種、CPU/GPUと精度差が関係する場合の条件 |

コミットだけで原板を特定できない場合がある。圧縮版と非圧縮版が別工程で更新されるため、採用した方を明示する。同じJSONLの論理内容を識別したい場合は、圧縮ファイル自体と展開後内容のハッシュを区別する。ハッシュ台帳を共用し、全試行で巨大ファイルを毎回複製・再計算しない。

## 5. 実施順序

1. [教科書](technical-analysis/README.md)から一つの現象を選び、反証可能な仮説にする。
2. [試行記録テンプレート](試行記録テンプレート.md)へ条件・比較・未使用期間・品質基準を記入する。
3. 原板の少数行から足・シグナル・約定・会計を追跡して、基準計算を確認する。
4. 条件を固定して全対象を計算し、セッションごとの純損益と未完了を残す。
5. Viewerで成功・損失・期限返済・欠損の代表例を確認する。必要な図だけ保存する。
6. 追加条件は比較対象を維持して評価する。未使用期間を見た後の修正は追加探索として扱う。
7. 試行結果を記録し、複数試行へ役立つ事実だけを `docs/` へ出典付きで移す。

特定の試行だけの経験則を、すぐ共通知見に昇格させない。「この条件・期間で確認」「反例あり」「未検証」を区別する。共通知見には元試行へのリンク、適用範囲、更新日を付ける。

## 6. 容量と計算資源

研究の標準はMarkdown、小さなJSON/CSV、約定中心のJSONLとする。他形式も必要性に応じて使える。容量の大きい中間生成物は `work/` に置き、再生成方法と必要な条件を残す。既存データを損失圧縮して置き換えない。

繰り返し利用する派生足や特徴量を共通キャッシュに置く場合は、元データ版・変換仕様・コード版から識別し、再生成可能とする。保存量に見合う計算短縮効果を確認してから恒久保存を判断する。

OSSの導入とGPUの利用は可能。導入時は名前・版・用途・必要なライセンス情報を記録する。今回は文書作成に必要がなかったため追加ソフトウェアを導入していない。将来の高速化でも、先読みのない基準計算との一致を先に確かめる。
