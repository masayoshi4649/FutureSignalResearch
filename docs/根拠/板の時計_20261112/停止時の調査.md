# 受信時計・価格時計・足公表時計の再確認

2026-11-12。コード・仕様・134時点の停止済み監査だけを読む非金融確認。新しいRaw/価格CSV本文、金融、追加2場は読んでいない。新採番・自然品質監査は行わない。141の入力は未選定。

## 結論

1. **現行ロガーは実際の処理時刻をメモリへ保持するが、book本文へ保存しない。** `../JP_OSE_Data`は取得済みファイルを配置するリポジトリで、元ロガーの実装は`../kabus-controller`にある。
2. **SourceRecordのscalar.receivedは消されていない。** ただし歴史再生のRaw reader（`readBoards`）が前段で`Received=CurrentPriceTime`と代入しているため、その値を実受信時計と呼べない。SourceRecordへ変換した時に実受信時刻を捨てた、という説明は不正確。
3. **CSV1分足は受信時刻で進む状態機械を反映し、OHLC採用には現値時計も使う。** `time`は足開始、`closed`は形成済み足の時間確定で、各メッセージの受信時刻や実際のClosedAtは保存しない。
4. Raw価格時計1分とCSV1分は別の測定。片方が生WSを全面的に再現する、片方の時計が真だとは断定しない。既存73場の各日のサーバ稼働バイナリ版も未証明である。

## どこに何の時計があるか

|段階|コード根拠|保持/利用するものと限界|
|---|---|---|
|WS受信処理|`../kabus-controller/kabus_websocket_snapshot.go: update`|`time.Now()`を取得しhistoryObserverへ渡す。これは当該ローカル処理の受信代理時刻で、取引所約定時刻やサーバ時計の正確さを保証しない|
|ロガーメモリ|`future_history_store.go: futureHistoryRecord / Observe`|receivedAt、商品内sequence、元payloadを保持。足生成のApplyへreceivedAtを渡す|
|book保存|`future_history_archive.go: archiveSession`|`record.payload`と改行だけを書く。receivedAt/sequence/generationを各行へ付加しない|
|book API|`future_history_store.go: ReadRaw`|from/toの絞込みにはメモリreceivedAtを使うが、送る本文はpayloadだけ。snapshotヘッダーのasOf/sequenceは各行の受信時刻ではない|
|データ取得|`../JP_OSE_Data/README.md`|サーバlogのファイルを取得。取得/圧縮時のmtimeやgzip時刻から各原行の受信時刻を復元できない|
|旧Native再生|`work/111元時計の連続再現/input.go: readBoards`及び元三手法input.go|CurrentPriceTimeをparseしてBoard.TimeにもBoard.Receivedにも代入。受信時刻を測定して読み出す経路ではない|
|SourceRecord|`work/104Source再形成CLIの準備/record.go: Step`と`.../tape.go: ProjectQuote`|Time/Received/Index/SourceLine/Last/Bid/Ask/QuoteOK/ATR等11値をscalar保存。完全ObservationはSHA、Source通知はdeltaとして保存。SHAだけから元WSや全特徴は復元できない|
|現在の固定取得reader|`work/133固定取得の正逆評価器/reader.go: decodeRow`|CurrentPriceTime→Quote.Clock/Time、採用Index/物理SourceLine、Last/最良BBOを射影。Quoteに受信時刻欄がなく、価格/時計不良や場外を別集計して除外|

SourceRecordは生bookとは別の、戦略呼出しと通知の保存形式である。scalarへ全板深度/数量時計/累積量/売買代金等を保存し直すものではない。完全Observation経路を戦略へ渡したことと、後のscalarだけで生WSを再現できることを同一視しない。新しい133系Quoteはさらに別の最小型で、SourceRecordという名前で一括しない。

CurrentPriceTimeはCurrentPrice/Last側の現値時計で、気配だけ更新されたメッセージの到着時計ではない。通常の直近約定/現値の意味と、quote更新・受信を分ける。APIの全価格ステータスを常に純粋な約定イベントだと推定することもしない。

## CSV1分足のtime/closed

`future_history_candles.go`の処理順は、`Advance(receivedAt)`→受信分の作業足→数量処理→価格の適格性確認である。

- 作業足の分はreceivedAtを立会開始基準で切り下げる。価格はCurrentPriceTimeが未来/後退でなく、この未確定の受信分に属する場合だけ採用する。遅れて届いた前分の価格を閉鎖足へ戻さない。
- `Time`はこの足の開始ラベル。価格自体は受信したCurrentPriceで、Bid/Ask中間値や配信元の当日High/Lowを流用しない。価格時刻と受信時刻の両方が採用可否に関わる。
- `closed=true`は、既に形成された足についてローカルの現在時刻が区間終端へ達したこと。1秒tickerからのAdvanceでも確定する。無観測の分を前値で埋めない。
- CSVは`time,open,high,low,close,volume,volume_complete,closed`の8列。receivedAt/ClosedAt/receive_seqはない。完成CSVを後から読んでも、各更新がいつ届いたかは戻らない。
- 5分足は存在する1分足を最大5本集約する。`closed=true`だけでは子1分が5本全部存在したと証明しない。

`volume_complete`は累積量の基準等に関する収集器の旗。初回・減少reset等ではfalseとなり、数量所属分はTradingVolumeTimeで確認する。trueでも取引所の全約定や未受信期間を完全に収録した証明ではない。1分timeを単純な「受信時計そのもの」「純約定時計そのもの」と呼ばず、上の混合定義を使う。

## 静かな時間を欠測と誤認し得る箇所

例えばWSの板更新が10秒ごとに届いていても、CurrentPriceTimeが09:00:00のままなら、価格時計readerのTimeは進まない。次の現値更新が09:01:01なら価格時計上は61秒飛ぶ。これは説明用の人工系列で、実データ件数を測ったものではない。

|経路|実装の扱い|言ってよいこと/言えないこと|
|---|---|---|
|128 Raw足生成`generator.go`|隣接採用Quote.Timeの差でgapを判断し、価格/量の未知・resetを付ける。EOFで受信タイマーを進めない|「価格時計の観測間隔が長い」は言える。「WS受信が61秒切れた」とは限らない|
|129/137系の短期1分|価格時計gap>60や次分への飛越で短期履歴をreset。新しい価格時計の後続行で前足を閉じる|無約定/Last時刻据置きでも同様に不足扱いとなり得る。実受信欠測の原因認定ではない|
|固定133系の先着観測|価格時計差>300等でgap_censored/BBO gapを判定|保守的な観測不足判定と、実際の通信断という説明を分ける|
|CSV収集器|実処理時刻は進むが、その受信分に属する現値を得なければ価格足を新設しない|空の分は「無観測の分」。約定なし/気配のみ/切断/遅着棄却等をCSVだけでは完全識別できない|

同時計の原行を保存したことは受信時刻を得た意味ではない。物理行/採用Indexは順序の根拠として保持できるが、取引所全イベント連番や正確な経過秒ではない。静かな相場と収集漏れの実発生件数は今回未計測。

## AvailableAt/DeliveryAtも別の時計

122/115のCSV公開器は完成子足のEnd+60等をNominalAvailable/AvailableAtとし、研究の観測行でDeliveryAt/ObservedAtを付ける。128の即時/60秒遅延も価格時計上の配送モデルである。これらは「研究モデルでいつ使用を許したか」を表し、bookに失われた実receivedAtを復元した値ではない。

CSV完成値を前倒ししないモデル上の因果性は検査できるが、実際に同じ内容がその時刻にWSから利用可能だったという証明とは異なる。134のCSV/Raw率差を、この時計1要因だけの効果や片方の先読みと断定しない。OHLC採用、閉鎖、数量、助走seed、配送窓も別の形成差として残す。

## 受信時計を使う新モデルは可能か

確認済みの現行保存仕様と既存の限定証跡だけでは、当該73場全行を正確なreceivedAtで再生できると認定する根拠がない。現行ロガー自身のreceivedAtをbookへ付加する経路はなく、SourceRecord/完成CSVからも戻らない。一方、別形式の行や対応するサーバ時刻ログ/sidecarが存在すれば可能性は変わるため、その存在・全行結合は未確認として残す。mtimeやCurrentPriceTimeへ架空の受信時刻を与えるなら、明示した仮定モデルであり実測モデルではない。

今後の収集は元payloadを保持し、別sidecar等に`payload_sha256 / book物理行 / receive_seq / session_generation / connection_id / received_at_utc / 接続断・再接続`を保存する案が考えられる。ローカル処理時刻・現値/量時計・指標公表時計を別欄にする。既存ロガーや保存形式は本作業では変更していない。

141入力の選定前に行える非金融監査と、Root F0後だけの限定キー検査案は[品質監査案](品質監査案.md)。今回は以前の2行のキー確認証跡を参照しただけで、新しい自然監査は実行していない。コードの指紋と確認範囲は`確認の記録.json`へ保存する。
