# 入力と数量の監査

確認日：2026-10-31。複合テクニカルの比較に先立ち、損益を参照せず入力を監査した。後続3場についても、この監査ではシグナル・注文・損益を計算していない。

## 1. 対象と固定する入力

NK225・TOPIXとも60セッション、2026-09-21_Day〜2026-10-30_Nightを確認した。探索範囲は各57場の2026-10-29_Dayまで。後続の10月29日Night・30日Day・30日Nightは、最終条件固定後の確認用として分ける。

原板は圧縮版があれば採用し、なければ生JSONLを採用した。展開内容SHA256、元の相対パス・サイズ・更新日時・物理行数、場内限月の一意性を台帳へ保存した。全120入力は日経平均先物26/12またはTOPIX先物26/12のラージで、mini・microの執行板ではない。

原板18,006,307行から3,746,068状態を保持し、連続する完全同一状態14,260,239件を省略した。120個の圧縮キャッシュの合計は**15,216,959バイト（約14.51MiB）**。採用原ファイルは圧縮・非圧縮が混在して合計4,427,742,224バイトであり、全JSONLの展開後サイズとは異なる。原板のコピーは作成していない。

作成コードは[データ準備.py](../../scripts/複合検証/データ準備.py)、合成データによる確認は[データ準備の検証.py](../../scripts/複合検証/データ準備の検証.py)。生成先はGit管理外の `work/複合検証/` で、詳細台帳は `入力キャッシュ台帳.json`、数量集計は `数量監査.json` にある。試行側では再現用の軽量台帳を固定する。

## 2. 二つの時計とCSV生成コード

提供元の公式仕様では、`CurrentPriceTime` は現値時刻、`TradingVolumeTime` は売買高時刻である。PUSHは値の更新に応じて配信される。いずれも、そのJSONをアプリが受信した時計ではない。[kabuステーションAPI・時価PUSH仕様](https://kabucom.github.io/kabusapi/ptal/push.html)（2026-10-31確認）

今回、隣接リポジトリのCSV生成コードを発見した。

| 一次コード | 確認できた処理 |
| --- | --- |
| [future_history_candles.go](../../../kabus-controller/future_history_candles.go) | `receivedAt` で現在の分を進め、価格時計と数量時計を個別に検査して更新 |
| [future_history_store.go](../../../kabus-controller/future_history_store.go) | メモリ内では受信時計と連番を保持し、生JSONと足を更新。毎秒の確定処理もある |
| [future_history_archive.go](../../../kabus-controller/future_history_archive.go) | 原板JSONLへはpayload本体だけを出力し、受信時計・連番を追加しない。足はCSVへ保存 |

確認したリポジトリのコミットは `7a38c505db71644ff32d936538e7625e74d4f685`。分足生成コードは2026-09-21のコミット `0317c1e16a43542b45f814a81489a641b6df7a5f` に追加されていた。ただし、実際の収集サーバーの稼働バイナリがこの版であったかは未確認である。

現行コードでは、受信時刻で足を確定し、価格時計が受信分と同じ場合だけ価格を取り込む。確定後に届いた前の分の更新は訂正に使わない。数量も同様で、遅着分は累積基準だけ進め、差分を現在の足へ加えない。したがって、**原板の価格時計だけで作り直した足と、受信時刻で確定したCSVが必ず一致するわけではない**。これは処理仕様として確認した機構であり、過去の個々の差分の原因を稼働版まで確定したものではない。[既存の足差分調査](../../study/00001_MACDと方向条件の比較/足差分の確認.md)

### volume_completeの意味

コード上の `volume_complete` は、数量の基準を取得済みで、その足の途中に累積減少等の再基準化がなかったことを表す。初回累積値を区間数量として全量計上せず、初回と減少時は基準を取り直す。

`true` は、通信欠落・遅着・未観測の約定が一切ないという証明ではない。5分CSVは存在する1分足だけを合算し、各足の旗の論理積を取る。1分足がない枠の存在だけで、5分全体を自動的に不完全へ変える実装ではない。

## 3. キャッシュが保持するもの

各状態は `now,line,last,bid,ask,valid,volume,volume_time` を持つ。時計・価格・数量はfloat64、物理行はint64、`valid` は真偽値。欠測はnpz内のNaNとし、JSONの台帳へNaNを書き込まない。

- `now` は価格時計、`volume_time` は数量時計。欠測・場外・後退もキャッシュには残し、消費側で価格時計を選別する。
- `bid` は `Buy1.Price`、`ask` は `Sell1.Price`。`valid` は正の `bid < ask` と両側数量1以上だけを表す。場内時計や有効なLastまで含む旗ではない。
- `line` は空行も数える元の物理行。連続同値を省く場合、最初の行番号を残す。
- 同じ価格時計でも、Last・BBO・正常性・累積数量・数量時計が変われば保持する。NaN同士を同じ欠測と扱って比較する。

この省略は1枚のBBOモデルに必要な状態を保つためのもの。数量がともに1以上のまま2枚から8枚へ変わる等の情報や、10段全板を残す汎用キャッシュではない。将来、多枚数の板消費等を扱うなら別の入力仕様が必要になる。

## 4. 今回採用する数量の定義

数量は**価格時計で利用可能な観測累積差分量**と呼び、正確な全約定数量や既存CSVのvolumeとは呼ばない。

1. 場内で単調な価格時計 `now` を用いる。有限・非負の累積数量と、`volume_time <= now` の状態だけを数量の更新へ採用する。
2. 初回、累積数量減少、数量時計後退、価格時計の足欠損後は基準を再設定し、その足を基準不完全とする。セッション最初の足も不完全とする。
3. 正常な増分は、その値を採用した `now` の5分区間へ計上する。過去の数量時計の足へ遡って配り直さない。
4. `volume_time > now` の行は数量を採用しない。後続の行で利用可能となった累積値から差分を取得する。独立した受信時計がないため、価格時計モデルの下での保留である。
5. RVOLに使う直前20足の履歴は当セッション内だけで作り、現在足を分母へ含めない。不完全足・欠足で履歴を切る。

ここでの「基準完全」は、上記の観測モデルで基準が継続していることだけを意味する。実際の取引全件を収録したという意味ではない。1行の累積値を重複して加算せず、同秒内の増分も原順で処理する。

## 5. 全120場の数量監査結果

場内の有効価格時計で扱った3,729,969キャッシュ状態では、数量時計はすべて価格時計と等しかった。有限・非負数量の欠測、数量時計欠測、数量時計の先行・遅延、採用累積減少、採用数量時計後退は**いずれも0件**。今回の範囲の観測結果であり、将来も常に同期する保証ではない。

| 指数 | 範囲 | 場数 | 価格5分足 | 基準完全足 | 直前20数量足を使える足 |
| --- | --- | ---: | ---: | ---: | ---: |
| NK225 | 探索範囲 | 57 | 6,726 | 6,649 | 5,418 |
| TOPIX | 探索範囲 | 57 | 6,731 | 6,662 | 5,496 |
| NK225 | 後続範囲 | 3 | 393 | 390 | 330 |
| TOPIX | 後続範囲 | 3 | 393 | 390 | 330 |

探索範囲の基準不完全はNK225が77足、TOPIXが69足。各57場の初足と、欠足区間後の再基準化20回・12回によるものだった。欠けた5分枠そのものは21枠・16枠。後続各3場は初足3本だけが基準不完全だった。

原行全体では時計欠測73,816件、時計後退63件等があり、場外や準備中の記録を含む。場内・単調時計への選別後の上表と混同しない。キャッシュはこれらも保持しており、`valid` だけで全状態を取引可能と判断しない。

## 6. 採用可能性と比較の限界

今回の定義では数量そのものの欠測が大幅にある状態ではなく、観測差分量による比較へ進む入力条件はある。一方、直前20本の助走と欠足後の再開によって利用可能な足は減る。数量条件を付けた候補だけ開始を遅くすると、数量条件の効果と母集団の違いを混ぜるため、比較候補の共通助走と利用可能条件を先に固定する。

観測差分量は約定側別フローでも、参加者の新規資金でもない。これを重みに作るVWAPも、現物の全参加者やmini・microの平均建値ではない。受信時計が原板へ残らない限界は、時計同期が今回全件で一致していても解消しない。

入力準備の再現は次のコマンドで行う。既存キャッシュは元ファイルのサイズ・更新日時とキャッシュSHA256を検査し、変更を検出したら停止する。別の版を作る場合は保存先を分ける。

```text
python -X utf8 scripts/複合検証/データ準備の検証.py
python -X utf8 scripts/複合検証/データ準備.py
```

この文書は入力と数量の利用条件をまとめたもので、数量条件の収益性を立証した結果ではない。

2026-11-04の追加PDCAでは、[NK225全65場の数量台帳集計](数量台帳の追加集計.md)を作成した。00008の保存済み監査の再集計であり、新しい原板の独立再監査とはしない。1/3分で数量条件を使う場合は、その足幅の集約・準備の検査を別に必要とする。
