## 2. 原板と分足の実物

確認したセッションの構成は次のとおり。

```text
JP_OSE_Data/future/
  NK225/2026-09-21_Day/
    book.jsonl
    book.jsonl.gz
    candle_1min.csv
    candle_5min.csv
  TOPIX/2026-09-21_Day/
    同じ種類のファイル
```

`book.jsonl.gz` は JSONL の gzip 圧縮版。解析時は圧縮ファイルを順次読み、試行ごとに解凍コピーを保存しない。データ取得処理は生の JSONL を転送し、圧縮版の更新は別工程であるため、生と圧縮版が両方あっても最新性・同一性を未確認のまま同じ入力と扱わない。[取得処理の説明](../../JP_OSE_Data/README.md)

NK225 の `2026-09-21_Day` の確認時ファイルサイズは、生の原板90,966,689バイト、圧縮原板1,140,467バイト、1分足21,643バイト、5分足5,275バイトだった。1例であり、平均サイズや将来の容量見積りではない。

### 原板の項目

原板1行には板の複数段・現在値・出来高などがまとめて入る。確認した先頭付近には次の項目があった。

| 項目 | 確認できた内容 | 研究上の扱い |
| --- | --- | --- |
| `Symbol`、`SymbolName` | 銘柄コードと、例として「日経平均先物 26/12」「TOPIX先物 26/12」 | 指数名だけでなく限月も照合する |
| `CurrentPrice` | 現在値。開始直後に `null` の行がある | 欠測を0円や前値に変換して売買しない |
| `CurrentPriceTime` | `+09:00` 付き価格時刻。同じ時刻が複数行に現れる | 受信時刻と区別し、物理行順も保存する |
| `Buy1`〜`Buy10` | 各段の `Price`、`Qty`。第1段には `Sign` もある | Viewer は `Buy1.Price` を買気配とする |
| `Sell1`〜`Sell10` | 各段の `Price`、`Qty`。第1段には `Sign` もある | Viewer は `Sell1.Price` を売気配とする |
| `BidPrice`、`AskPrice` | 先頭付近の実物では、前者が `Sell1.Price`、後者が `Buy1.Price` に一致する例がある | 英語名だけから売買方向を決めない |
| `TradingVolume`、`TradingVolumeTime` | 数値と時刻、または `null` | 累積値の起算・リセット規則を収集仕様で確認する |
| `VWAP`、`TradingValue` | 数値または `null` | 原提供値の集計起点を確かめる |
| `OpeningPrice`、`HighPrice`、`LowPrice` と対応時刻 | 数値または `null` | 過去のどの期間を集計した値か確認する |
| `ClearingPrice`、`PreviousClose`、`CalcPrice` | 清算値・前値等とみられる数値 | 発注時点の約定可能価格の代用にしない |

確認した NK225 の冒頭では、`CurrentPriceTime` がない板、`Buy1.Price = Sell1.Price` の板、一時的に買気配が売気配を上回る板があった。通常の連続売買の約定モデルへそのまま流さず、寄付き前・気配更新・欠測等の状態として区別する。Viewer が正常な評価に用いる条件は、正の価格と `Buy1.Price < Sell1.Price` である。[原板の読取処理](../../SessionTradeViewer/data_io.go)、[含み損益の評価処理](../../SessionTradeViewer/ledger.go)

### 時刻の限界

確認した行には、独立した受信時刻や取引所の全イベント連番を確認できなかった。`CurrentPriceTime` は価格の時計であり、板だけが変わった行の実際の到着時刻を必ずしも示さない。Viewer も「受信時計ではありません」と品質情報へ出す。[数値応答の構築](../../SessionTradeViewer/data.go)

したがって、同じ価格時刻の複数行を1行に潰すと板更新順序を失う。一方、物理行順だけでミリ秒単位の通信遅延や取引所での注文順位まで復元できるわけでもない。板更新時刻の厳密な再現が必要な手法は、追加収集仕様の確認が先になる。

Viewer は時計欠測行と後退行を描画から除き、品質件数へ残す。同時計行は原順を保持する。研究エンジンが別の除外条件を使う場合は、表示と検証に差が出ることを記録する。[原板の読取処理](../../SessionTradeViewer/data_io.go)

### 分足の列

実物のヘッダは1分足・5分足とも以下だった。

```csv
time,open,high,low,close,volume,volume_complete,closed
```

NK225 の最初の1分足には、次の1行を確認した。

```csv
2026-09-21T08:45:00+09:00,65180,65200,64990,65020,102,false,true
```

`time` は時差付き日時、価格4列、出来高、2つの真偽値がある。列名から想定できる意味と、生成処理で証明できた意味を区別する。今回、CSV の生成コード・累積出来高の差分計算法・`volume_complete` の判定条件・足の端点処理までは確認できていない。`closed=true` の確認だけで、データ到着の完全性や即時利用可能性まで保証されたとは扱わない。`volume_complete=false` の足は、とくに出来高・VWAP研究の除外または別評価候補となる。

原板の行数は約定件数ではない。`TradingVolume` を全行で足し合わせず、差分を使う場合は同時計・重複・欠測・リセットを検査する。差分出来高が分かっても、その間の全約定価格がなければ正確な約定単位の VWAP を再構成できない。[指標の計算](technical-analysis/02_指標の計算とシグナル.md)も参照。

## 3. 原板から分かること・分からないこと

| 利用目的 | 現状の位置付け |
| --- | --- |
| ラージ価格の時系列から確定足・指標を作る | 欠測・時刻・足区切りを検査すれば候補になる |
| ラージの表示された板数量・スプレッドを特徴量にする | 各行の意味と価格時計の限界を踏まえて検証する |
| mini・micro の方向判断へラージを利用する | 研究仮説として可能。執行価格まで同一とはしない |
| mini・micro の正確な成行約定や指値待ち行列を再現する | 対象商品の板・約定・注文順位がなく、現存ラージ板だけでは確定できない |
| 価格に触れた指値がすべて約定したとする | 待ち行列と取消を無視した仮定。主結果には無条件適用しない |
| 取引所の全約定を再現する | 板スナップショットからは保証できない |
| 指標計算結果を Viewer に重ねる | 現在の文書化された入力形式には汎用指標系列の登録欄がない |

指標値はパラメータから再計算し、必要なら売買判断時だけ小さな補助記録を残す。Viewer が対応していない列を追加すれば描画される、とは想定しない。[入力型](../../SessionTradeViewer/types.go)

## 4. Viewer を原板の複製なしで使う

`conf/viewer.toml` の2つのルートを、原板と研究資料の実際の配置へ合わせる。以下はこのPCの配置例であり、この文書作成時に設定を書き換えたものではない。

```toml
[paths]
data_root = "S:/GitHub/masayoshi4649/JP_OSE_Data/future"
resource_root = "S:/GitHub/masayoshi4649/FutureSignalResearch"
default_catalog = ""
```

TOML 内の相対パスは実行ファイルのフォルダが基準になる。`resource_root` を研究リポジトリに合わせると、画面やAPIから `study/00001_要約/一覧.resources.json` のように指定できる。Windows・Linux間で移す場合はこの設定を調整する。[起動と設定](../../SessionTradeViewer/README.md)、[パス解決](../../SessionTradeViewer/config.go)

現実装の「価格だけ」用自動セッション列挙は `book.jsonl` の存在を検査しており、圧縮版だけのフォルダは列挙されない。ファイル読取自体は gzip に対応するため、圧縮版を使う研究一覧では次節のように `market_path` を明示する。既定パスが自動で `.gz` に切り替わるとは扱わない。[一覧検出](../../SessionTradeViewer/catalog.go)、[gzip読取](../../SessionTradeViewer/data_io.go)

## 5. 試行内に置く最小の Viewer 形式

以下は仕様説明用の架空の2約定であり、検証結果や実約定ではない。金額・手数料は例示値で、実際の料金ではない。

`study/00001_要約/一覧.resources.json`：

```json
{
  "schema_version": 1,
  "path_base": "catalog",
  "resources": [
    {
      "id": "研究例",
      "title": "形式説明用の架空取引",
      "symbol": "NK225",
      "session": "2026-09-21_Day",
      "product": "NK225micro",
      "method_id": "仮説例",
      "point_value": 10,
      "pnl_format": "trades",
      "pnl_basis": "net",
      "pnl_path": "約定.trades.jsonl",
      "market_path": "NK225/2026-09-21_Day/book.jsonl.gz"
    }
  ]
}
```

同じフォルダの `約定.trades.jsonl`：

```jsonl
{"id":"約定1","timestamp":"2026-09-21T09:00:00+09:00","type":"LongN","position_id":"建玉1","price":65100,"qty":1,"fee_yen":20,"method_id":"仮説例"}
{"id":"約定2","timestamp":"2026-09-21T09:05:00+09:00","type":"LongR","position_id":"建玉1","price":65120,"qty":1,"fee_yen":20,"method_id":"仮説例"}
```

この例の会計上の純損益は `(65120−65100)×10×1−20−20 = 160円`。ラージ板を用いてmicroの約定可能性まで立証した例ではない。`point_value` は1価格単位・実枚数1枚当たりの円で、数量をラージ換算枚数に置き換えない。

`path_base: "catalog"` では `pnl_path` を一覧ファイルの親フォルダから解決する。一方、`market_path` は常に `data_root` 基準。画面ではサーバー上の一覧パスで開く。生JSONをブラウザから送る場合には絶対 `base_dir` が必要となるので、可搬性を保つにはサーバー上の一覧を指定する方法が簡単である。[正式なデータ仕様](../../SessionTradeViewer/docs/データ仕様.md)

### 約定の意味

| `type` | 意味 |
| --- | --- |
| `LongN` | 買い新規 |
| `LongR` | 買い建玉の返済。執行する注文自体は売り |
| `ShortN` | 売り新規 |
| `ShortR` | 売り建玉の返済。執行する注文自体は買い |
| `Detach` | 管理対象からの移管。決済ではなく、損益も確定しない |

1行は注文要求ではなく約定片。分割約定は行を分け、`id` を一意にする。`qty` は正の整数、`timestamp` は時差付きRFC3339とし、対象セッション内で非減少順に記録する。時計の後退はエラーになる。部分返済は同じ `position_id` を指定する。新規と返済の対応を FIFO で推測しない。`fee_yen` はその片の費用で、省略時0。`pnl_basis: "net"` では新規時の費用も累積確定損益へ即時反映する。

同時刻の原板との対応には、任意の `source_line` に1始まりの物理行番号を指定できる。これは入力原板ファイルが同一である場合の対応であり、時刻の意味そのものを改善するものではない。原行のフィルタ後番号に置き換えない。[約定の読取処理](../../SessionTradeViewer/data_io.go)

Viewer は開始時の保有0を前提とし、セッション内の全約定を必要とする。同じ `position_id` に同方向の追加約定があれば加重平均建値を用いる。複数手法を同じ約定ファイルに保存し、一覧の `entry_method_id` で新規時の手法へ帰属させれば、返済手法が異なっても対象の全約定を表示できる。[台帳処理](../../SessionTradeViewer/ledger.go)、[手法別抽出](../../SessionTradeViewer/data_io.go)

原則として、1約定JSONLは同一商品・同一倍率とする。異なる商品はリソースに加えて `pnl_path` も分ける。約定行には商品別の列がなく、一覧の `product` は表示用の情報であって、それを指定するだけでは行を商品別に抽出しない。同じ約定ファイルを異なる倍率で読み直すと損益を誤計算する。

`Detach` で場末の保有を見えなくしても「持ち越しなし」の達成にはならない。本研究の終了判定は、実際またはシミュレーション上の全返済約定後に、買い・売り建玉と未約定注文がいずれも0であること。

### その他の入力と表示

独自会計を保存する場合は `pnl_format: "snapshots"` も使える。`timestamp` と保有枚数・確定損益・含み損益を必要な変化時に保存する形式で、欠測の含みは `null`。原板から含みを再計算しないため、独自評価の根拠を別途説明する。約定形式で足りる研究の標準にはしない。[状態形式](../../SessionTradeViewer/docs/データ仕様.md)

Viewer の分足は全原行から OHLC を作る。CSV の足をそのまま読む機能としては説明されていない。JST の時計分へ整列し、区間は `[開始,終了)`、場の終端だけ最後の足へ含める。保有・損益は区間末値なので、足内の最大含み損や一瞬の建玉は raw 表示で確認する。最終的に完成した足の表示値を、その足の途中で知っていた指標値として使わない。[足の仕様](../../SessionTradeViewer/docs/データ仕様.md)

## 6. 報告・画像と容量

標準成果物は、仮説と結果の Markdown、パラメータ・入力参照、集計、Viewer 一覧、約定片とする。売買理由を機械的に再現できない場合だけ、判断時刻・理由・必要な指標値を少量記録する。各試行への原板・全指標系列・毎ティックの含み損益・大量の画像の複製を避ける。

Viewer の `GET /api/chart` は、PNG・SVG・数値のURL、出所、指紋を返す。根拠の数値と画像を対応させて調査し、論点がある区間だけ必要に応じて保存する。画像取得URLには期待指紋が含まれ、入力更新で不一致なら再取得が必要となる。[画像API](../../SessionTradeViewer/docs/画像API.md)

例として、次の指定で登録した研究資源の1分足を取得する。日本語や区切り文字はHTTPクライアントでURL符号化する。

```text
GET /api/chart
  catalog_path=study/00001_要約/一覧.resources.json
  resource=研究例
  interval=1
  price=last
```

Viewer の値は表示幅に応じて縮約される。表示用の `prices` や `states` を再びバックテストの原入力として使わず、原板・原約定から会計とリスク指標を計算する。API の最終状態は約定の整合確認に用い、グラフから全件損益を読み取って集計しない。

再現用には、入力の相対パス、サイズ、ハッシュ、対象セッション、取得時点、コード版、パラメータ、価格系列、気配方向、除外規則、費用仮定を残す。大きな原板のハッシュは初回入力台帳で共用できる。入力が更新されたら別版として識別する。

## 7. 最初の損益算出前に解決する項目

1. 原板の価格時計・板更新時刻・受信順序の意味と、収集漏れの検出方法。
2. 元CSV生成処理、出来高の起算、`volume_complete` と `closed` の厳密な意味。
3. セッション・限月ごとの有効範囲、祝日、欠測、同時計、後退時計、交差板の件数。
4. ラージ観測と実際に売買する商品を分けた価格・スプレッド・費用モデル。
5. 強制決済の締切と、終端まで返済できないケースの扱い。

これらを確認できない部分は明示した仮定で検証し、実約定可能性を保証する成績として扱わない。[先物と執行の制約](technical-analysis/03_先物と執行の制約.md)へ続く。
