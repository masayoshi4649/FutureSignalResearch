# 保護返済後の実建玉と元手法の接続

確認日：2026-11-10。一次資料は固定純戦略43項目、111 Source/API、111 Actorと接続、旧94の固定方針。市場・Raw・Native本文は追加読取していない。コード・仕様・閾値は変更していない。参照位置と現物指紋は[コード参照索引](コード参照索引.json)に保持する。

## 確認した構造

**111の追加保護で実Positionがflatになっても、その約定は元Sourceへ通知されない。** Sourceは毎原行で判断を続けるが、Source側の建玉は自身の返済通知・約定で減るまで残り得る。「判断を停止している」のではなく、外側の実flatを知らない状態で保有管理・追加・元退出を判断する構造である。

| 層 | 所有する状態 | 111追加保護の実約定で更新されるか |
|---|---|---|
| 外側Actor | ActualPositionの残・予約・実現損益、純保護の床/L | 更新される |
| Source AdapterのPortfolio | Selected.Lots、注文/約定、DayのCanonical/政策予約 | 更新されない。Adapter自身の参照約定をOnFill/OnOrderDoneへ渡す |
| selected内の固定源 | Selected.Shadow、ShadowPending、SourceLots/親の残量 | 外側約定では更新されない。自身の元通知と参照約定で進む |
| さらに内側の基礎源 | S01/P05のShadow、D07等のResearchSource/ResearchBook | 外側約定では更新されない。独立した仮想所有・予約・親・待機状態を持つ |

111 SourceConsumerの返り値はerrorだけであり、実FillをSourceへ返す接続口はない。元Adapterが先に元通知を作り、独立複写を外側へ配送する。外側fillOrdersはActorの所有と会計を更新し、Portfolio.OnFillを呼ばない。この分離は旧94でも明示された設計である。

## 新規・再評価・数量への影響

- 外側Actorは各Source新規通知を一度だけ受理し、`entryBySource`へ受付0枚・取消も消費済みとして残す。`positionByHold`も同じ出生への再参加を拒否する。早期flat後に同じ通知を復活させる動作はない。
- 外側の空き枠は実残・未約定新規から計算するため、**後から届く別Sourceの新規通知**の受理可否・枚数は保護政策によって変わり得る。Sourceの通知列固定と、全政策の実新規集合固定は同義ではない。
- selected内部の空き枠はSelected.Lotsと同層の未完了注文を見る。外側だけflatになってもこの枠は戻らない。DayにはCanonicalの保有＋新規予約、親の`InitialSeen / Deferred / Cancelled / Rejected / Ended`、初回配分`Factor`等も残る。
- Dayの初回・追加は新しい元new通知を契機にする。既通知は`SeenSources`で除外される。夜間も元new通知、またはU165の既存待機を生存Source・新しい同方向帯等で解除する経路であり、実flatだけで再新規する経路ではない。
- 基礎源にも保有量0・予約なし・クールダウン等を要求する入口がある。たとえばResearchActiveの通常入口は`total==0`、`Pending`なし、`NextReady`以後である。外側の実残0を伝えなければ、この分岐の`total`は変わらない。逆に一律flat化すると、親・損益履歴・再準備条件まで元方式と異なる判断を生む。

なお、夜間の価格帯状態は市場分析の履歴であり、証券建玉と別物である。実flatになったからといって市場の帯・指標履歴まで消す必要がある、とはコードから言えない。

## 約定・取消APIが意味すること

`Portfolio.OnFill(Fill)`、`OnOrderDone(signalID)`、`OnOrderRejected(signalID)`は存在する。ただしOnFillは**当Portfolioに登録済みの注文ID**を要求し、対象建玉・方向・未約定量も照合する。Actor独自の保護注文IDをそのまま渡すと未登録注文として拒否される。過去の新規注文IDへの付替えも、別の返済注文の登録にはならない。

OnOrderDoneは取消を含む注文終了、Rejectedはその別名であり、保有を返済するAPIではない。Dayでは未約定予約の解放・初回拒否・未完了返済のRetry管理を行う。これを実Fillの代わりに使ってflat化することはできない。

Dayの`ExternalFillSelectedDay`も存在するが、共通帳簿が約定を反映した後にCanonicalを同期する政策内の経路である。単独でSelected.Lots、注文、Executions、Shadowを一括更新する口座APIではない。`Flatten / FlattenOwner`は登録済みの実玉へ返済要求を作れるが、`Forced / ForcedOwners`を保持して以後の新規を止めるため、返済後に通常再判断を再開する汎用保護APIとしてそのまま扱えない。

## 111の証明範囲と次の研究の違い

旧94/111の固定通知方式は、**同じ元通知列を各政策へ同じ原行で与え、実際に成立した取引の出口・費用・保護を比較する**ための有効な対照である。「元の入口を固定した出口比較」は、このSource通知列の固定を指す。同一の実新規時刻・価格・枚数による出口差だと述べるには、別途その群の同入口照合が必要になる。

次に考えられる統合は、同じ実験の単なる配線修正ではない。少なくとも次を分ける必要がある。

1. **選定実帳簿まで実約定を戻す**：実新規の部分約定・未約定取消・保護返済を、登録注文と所有IDを保ってSelected.Lots/予約/Canonicalへ反映する。実枠は戻せるが、内側の固定Shadowから新しい入口が出ることまでは保証しない。
2. **実flat後の再評価を新しく定義する**：どの源を固定参照として残すか、同じ親で再参加を許すか、初回/追加/待機履歴をどう扱うかを新試行で決める。再評価が成立した原行に新しい注文IDを発行する。古い通知の再生や、flatだけを理由にした新規とは区別する。
3. **基礎源の保有まで実約定へ同期する**：Shadow/ResearchBookの保有・予約・親、クールダウンや部分返済資格も整合させる必要がある。これは元の固定源自体を変更する研究で、111の元通知同体という証明を引き継げない。

いずれも、数量・所有・予約・政策内配分を部分約定ごとに一度だけ更新し、同原行のSource返済と保護返済の重複、取消後の遅着約定、残玉0、再起動を扱う必要がある。複数政策の実約定を一つの共用Sourceへ混ぜられない。選ぶ統合範囲によって政策別の戦略状態が必要になる。

時系列も別の論点になる。現在のSourceは当行Observeを終えてからConsumerへ配送し、Portfolioは同じIndexの二重Observeを拒否する。実Fillをいつ戦略へ反映し、次にどの原行で新規を再評価するかを事前に定義する必要がある。同期対象の層で元の参照Fillと実Fillを二重計上せず、参照として残すShadowとは分ける。元Sourceの費用0判断へ実費用を返すかも、単なる数量同期と同じ変更ではない。

ここで述べたのは将来の**新しい実取引を生む再評価**の研究候補であり、有利になるという実証結果ではない。未参加や退出後の仮想利益は採点しない。検証する場合も新しく成立した実取引の費用後損益・損失総額・DD・保護実績を対象とし、旧94/111の固定条件は対照として残す。
