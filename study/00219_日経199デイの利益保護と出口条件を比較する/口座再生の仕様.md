# 元181建玉への適用と、出口を変更した口座の再生

日経199_02の2026年9月21日〜11月20日の45デイを対象にした。元入口を生成する当時特徴・1分足・元注文の技術判定・新規原行と予約を[217の日経デイ再生](../00217_デイの利益集中と入口条件を比較する/日経/README.md)から引き継ぐ。全ての日が既使用。口座内では売買合計で日経225mini換算1枚、予約中・保有中の追加禁止、セッション開始一律待機なし、15:30までの全決済を維持する。

## 二つの集計

- **入口固定**では元の両側口座が取得した全181建玉それぞれに、同一の取得日時・価格・実側・元の幅と期限を与え、出口で生じた差を見る。この比較は個々の取得への適用で、枠の再予約は含まない。
- **口座再生**では全ての元の新規判断を元の原行順に戻し、出口候補ごとに予約から再計算する。決済時刻が早まると新しい取得が増え、別の元の取得が保有中のため消えることもある。元の初参加補完はその候補の当日履歴から判定する。売り買いは同一の1枠を共用する。
- どちらも包括的な最高値・安値は建玉記録の追加診断でのみ計算し、返済の発動条件へ渡さない。該当する取得の新規原行から実返済原行まで、清算可能側の各正常気配で現在清算した場合の最大・最小含み損益を求める。買いはBid、売りはAskを使い、往復費用を最初から差し引く。未知なら最終確認行までに観測した値に限る。全ての時計は原板価格時計。

## 板と予約

48バイトの原板索引をSHA256込みで読み、価格時計の単調性、元の取得と原行の対応を照合する。買い新規はAsk、売り新規はBidで取得を代用する。返済は反対の最良気配。板はラージ、金額は1pt＝100円。各既知建玉の費用は往復手数料77円と追加滑り1,000円、合計1,077円。

元入口・注文の競合は173の既存予約部品で再生する。決済済みの枠は決済秒の最後に解放し、決済時刻と同秒の候補には先に使わせない。日中15:29:00以後は新規・新規取得を打ち切る。場末を迎える建玉の返済は15:29:00に要求し、15:29:01から15:30までの最初の正常気配を使う。通常期限の返済は期限から30秒までの正常気配を使う。価格・気配の300秒超の空白、期限の有効気配不足は179の打切りを引き継ぎ、確定しない取引で保有枠を先に空けない。このモデルは複数秒にまたがるデータの途切れやラージとminiの板差、実注文の待ち行列を再現しきれない。

元IFDは試行213の価格索引による探索と正常原行の走査を併用。元の181件の売買、幅、期限、取得・決済の原行・価格・時刻、費用後収支など17属性が既存正本と一致すること、各場の予約と保有を合わせた最大使用枠が1以下であることを検査する。新しい出口での実際の返済額は、注文を発動した価格から転記せず、出口モジュールが指定する実行原行の反対側気配から再計算する。

## 再現

リポジトリ直下で、先に[218の固定入口の再現手順](../00218_日経199デイの売買方向と建玉日時を検証する/片側対照/README.md)で217と216が参照する旧データ・原行索引を準備する。過去の中間を消していても[213の復元資料](../../inputs/00213_日経型TOPIXの純入口/README.md)から旧ソースを復元できる。Python・NumPyと共用原板へのアクセスを必要とする。

```powershell
$trial = (Get-ChildItem study -Directory -Filter '00219_*').FullName
python -X utf8 (Join-Path $trial '口座再生.py')
```

作業領域 `work/219出口/比較元帳.json` の第一階層は「口座再生」「入口固定」、第二階層は候補IDである。`work/219出口/再生照合.json` に対象日・元照合属性・各場の取得数・再生コードと出口定義のSHA256を保存する。特定候補だけを取り出して再生する場合は `--候補` にIDを並べ、`--出力` で別の検算先を指定する。
