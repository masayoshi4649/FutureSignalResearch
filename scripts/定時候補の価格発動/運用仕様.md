# 定時候補を将来価格で発動する運用

作成・人工確認日：2026-11-06。試行67の独自運用仕様。実市場の成績はこの文書で扱わない。

## 入出力と責任

公開入口は `replay(events, slots, conditions, session, candidate_id='G0', bounds=None)`。標準ライブラリのみを使用し、[固定49運用](../定時帯反応/運用.py)を固有名で読み、約定・保護・現金算術を継承する。旧ファイルや大域変数を変更しない。市場ファイル、特徴、モデル、教師を読み込まない。

- `events`：原行順の反復可能列。各行は `{now,line,last,bid,ask,valid}` の6キーだけ。`line` は正の整数でstrict昇順、`valid` は元のBBO/数量正常旗。正常BBOは `valid is True` かつ有限正 `bid<ask`。非有限時計・後退時計は固定49どおり除外し、該当slotとの結合は拒否する。価格時計を受信時計と呼ばない。
- `slots`：固定49の純判断だけ。`scheduled,time,line,side,role,atr,D,reason,ready,slot_id`。実slotは予定から0〜30秒以内の最初の有限非後退時計行へrootが結合する。欠測は `time=scheduled,line=None,ready=False` のplaceholder。未来labelや特徴辞書を渡すことは禁止する。
- `conditions`：`slot_id -> {high,low,source,expires}`。`high/low` は有限正、`high>=low`、`expires=scheduled+900` かつ実判断時計より後・強制時計より前。`source` は不透明な出典辞書。当場・公開完全3分・最新・当時可視の保証はroot側で行い、エンジンは再計算しない。
- `session`：場名。`bounds` 未指定ではDay強制15:35・終了15:40、Night強制翌05:50・終了05:55。終了は半開 `now<end`。

返り値は固定49と同じ `decisions,trades,fills,closed,trail,orders,quality,metrics,final_state,session,candidate_id,bounds` に `conditions,condition_trace` を加えた辞書。Viewer約定は固定49の標準形、`closed` は英語キーの固定49形を使う。原入力は変更しない。

## 当時判断と条件登録

定時判断の優先は、欠測又は正常BBOなし→判定不能、既存pending→処理中、保有→保有継続、既存watch→処理中、特徴未準備→判定不能、強制以降→待ち、side0→待ち、残りの純候補→条件設定判定。

保有継続には特徴ready・Lastを要求せず、正常BBOだけを要求する。無効BBOは保有中も判定不能を優先し、保有flagは別に残す。新規候補には役割が順行又は反転、有限正ATR、有限 `5<=D<=125` が必要。

設定行は正常BBOに加えて有限正Lastが必要。Last不正なら当時actionは判定不能、条件結果は観測不足、未登録とする。watchを開始していないため、これだけでは損益品質注意を追加しない。設定時に買いLastがhighをstrict超過、又は売りLastがlowをstrict下回るなら既超過として待つ。等号およびhigh=lowは登録できる。

受理actionは **条件登録**。元slotの方向・役割・ATR・D・理由・予定時計・実判断時計・原行を固定し、将来の指標で更新しない。価格否定線は今回追加しない。一監視、一pending、一枚の上限を守り、同枠での再登録・再発動をしない。

## 将来発動・約定・満了

1. 設定key `(slot.time,slot.line)` よりstrict後の原行を監視する。同価格秒の後行は利用できるが設定行そのものは使わない。
2. 監視用の正常観測は正常BBO **かつ** 有限正Last。買い `Last>high`、売り `Last<low` で発動し、新規要求を出す。等号は未発動。watchはこの時点で消費する。
3. 注文の `request_time/request_line` は発動key、`order.slot` は元定時の全文。発動で元slotのtimeやATR/Dを上書きしない。約定は要求+1価格秒以降かつ後原行の最初の正常BBOで買いask・売りbid。発動後のLast不正は正常BBO約定を妨げない。飛越した線価格では約定しない。
4. 全条件は元予定+900の独立timerを持つ。次定時等号ではwatchと、その条件に由来するentry pendingをfillより前に取り消す。返済pending・保有は取り消さない。最終枠も同様で、寿命を強制時計まで延ばさない。
5. 新規TTL30秒は固定49のまま。同秒の正常BBOはTTL等号でもfill可能だが、条件満了・強制・終了との等号では新規fillできない。
6. 強制返済は原行がなくても独立timerで要求し、最後に既知だった原行を出典とする。fillは強制+1秒以降の後行かつ終了未満。最後値による架空返済をしない。

## 監視の観測不足と損益品質

監視時計の起点は設定time。正常BBOと有限正Lastの両方を満たした原行だけで最終観測時計を更新する。

- 任意の有限非後退時計原行で、最終監視時計から300秒をstrict超えていれば、当行BBO/Lastの正常性と突破より先に観測不足取消とする。当行keyを終了根拠に残す。
- 原行が到着しなくても満了timerで `expires-last_observation_time>300` を検査する。300等号は正常な未発動、超過は観測不足。満了timerの原行出典は境界より前の最後に既知の行。
- 監視開始後の不足は `watch_quality=True`、当場の損益注意、期間全体の確定対象額nullへ接続する。登録済だが新規約定なしとして保守待ちにも含める。未発動と混ぜない。
- 固定49の通常気配gap品質は別の責任。建玉・返済pendingをまたぐ正常BBO gap>300秒、場末未解消は従来どおり損益注意。空き時間・新規pendingだけのgapは場診断とし、それ単独では損益注意にしない。

品質nullでも観測額と約定台帳を残す。完結観測額は完結取引だけの合計、台帳観測額は未解消建玉の新規片道費用も差し引く。確定可能と観測できた現金を同一視しない。

## 連続保護と費用

固定49をそのまま呼ぶ。実返済BBO方向差を `r`、過去最高方向差を `h=max(0,h,r)`、追尾線を `L=max(前L,-125,h-D)` とする。初期線 `max(-125,-D)`。現在 `r*10-122>0` strictで利益旗を起動し、以後 `L>=0`。`r<=L` で返済要求。返済pending中のh/L/利益旗は凍結し、実保有のMFE/MAEだけを更新する。固定250利確は追加しない。

同じ実約定に対して `pnl0=方向価格差*10-22`、`pnl5=pnl0-100`、`pnl10=pnl0-200`。Viewer片道 `fee_yen=61` は手数料11円と参照滑り5pt相当50円の和。約定価格へ滑りを加えない。名目新規床は費用後黒字を保証しない。

## 保存literalと活動

`operation.conditions[slot_id]`：

| キー | 内容 |
| --- | --- |
| condition / origin_slot / slot | 入力4キーの深い複製／slot_id・場・予定・判断時計・行／元純slot全文 |
| registered / watch_started | 条件登録を受理したか。両者は同じbool |
| status | 未評価、監視中、注文待ち、終了。出力時は評価を終えている |
| condition_outcome | 未登録、既超過、観測不足、未発動、発動未約定、約定 |
| condition_reason / watch_quality | 登録を妨げた理由又は終端理由／開始後の監視不足bool |
| last_observation_time | 監視の最後の正常BBOかつ有限正Last時計、未登録None |
| trigger | 未発動None、発動後 `{time,line,last}` |
| request_time / request_line / order_id | 発動要求の出典と注文ID、未発動None |
| entry_filled / entry_time / entry_line / entry_price | 実新規の成立と実BBO約定情報 |
| end_time / end_line | 条件終端の出典。保有後の退出時計とは異なる |

`condition_trace` は条件登録・条件未登録・条件発動・条件取消・条件新規取消・条件新規約定の遷移だけを保存する。全tickやSOURCE全文の重複転記は行わない。元判断のactionは結果判明後も変更しない。

活動の全予定枠分母を維持し、主待ちは当時actionが待ちの数だけ。保守待ちは **待ち＋判定不能＋条件登録したが実新規約定なし**。登録前の既超過は待ち、設定観測不足は判定不能、登録後の未発動・監視不足・発動未約定は条件未約定へ入る。保有・処理中は非待ち。条件登録の指示だけで保守活動を達成したことにはしない。

`metrics` に `条件登録数`、`条件未約定` を追加。`主待ち率` と `保守待ち率上限` を分け、`待ち率条件適格` および `quality.活動評価適格` は保守上限<=50%を用いる。`全枠判定可能` は判定不能0の別flag。
